# The sims that were already failing when the nightly job was switched on.
#
# .github/workflows/sims.yml goes red only for a sim that fails and is NOT listed here, so this
# file is what makes the job readable rather than red every night. It is a record of a debt, not
# a list of things that are fine. The job also reports any sim here that starts passing, so the
# entry can come off - otherwise the list rots into an excuse.
#
# CI IS THE AUTHORITY, NOT A LAPTOP. This list was first built from a local run and the first
# CI run disagreed with it in both directions: fourteen entries passed on a runner and seven
# sims that pass locally failed on one. Most of that was a content checkout twenty-three
# commits stale - marksofgrace was listed here as wanting a varp that "exists nowhere in the
# content", and the varp was in rooftop.varp all along. The list now says what CI saw.
#
# HOW IT WAS MEASURED. All 303 sims that exit non-zero on failure were run (2.8 hours), then
# every failure was run AGAIN one at a time. That second pass matters: 48 of the 85 that failed
# in the parallel run passed when run alone, because four shards were sharing the engine's
# SQLite files under data/ and because '../content' pointed at an empty directory skeleton on
# the machine doing the measuring. Only the 37 that failed both times are here.
#
# So the real state was 266 of 303 passing. That figure is from the unseeded baseline and has not
# been re-taken in full since; the entry count below is the number that is trusted.

# THE DICE ARE FIXED NOW, AND THIS LIST HAS BEEN RE-MEASURED AGAINST THEM. Everything above was
# measured with the suite rolling a fresh dice each run, which is why it would not settle: the
# fourth CI run had droprate, gwdskirmish, rdreach and fremtrials2 each fail TWICE IN A ROW while
# all four passed on a laptop, so retry-once could not absorb it. The cause was not state leaking
# between sims - each one is its own process - it was two unseeded generators: the module-global
# JavaRandom behind the content's `random` op, and the engine's own direct Math.random calls for
# npc wander steps and hunt targets. gwdskirmish counted 52 npcs in the god chamber on one run and
# 50 on the next for exactly that reason. Both are seeded from tools/sim/harness.ts now.
#
# THE FIFTH RUN WAS THE FIRST SEEDED ONE, and it is the measurement this list now records:
#
#   - ZERO flaky sims across all eight shards. The retry is still in the job and never fired once.
#     That is the thing to watch: it is an instrument now, and a FLAKY line means something STILL
#     varies between two runs of one commit.
#   - CI AND THIS MACHINE AGREE, six for six. templetrek and trollromance fail in both;
#     droprate, gwdskirmish, rdreach and fremtrials2 pass in both. The disagreement that made this
#     file worthless for a week is gone.
#   - Five entries came off: fletching, quest_rag_run, randomevents, quest_myreque2_run,
#     quest_druidspirit_run.
#
# AND A FIXED DICE DOES NOT ONLY REVEAL BUGS - IT ALSO PINS DOWN FRAGILE CHECKS, which is the
# honest way to read the two new entries. templetrek and trollromance pass three times out of
# three on a free dice and fail every time on seed 1. They are not bugs the seed uncovered; they
# are assertions that depend on the roll, and they would have failed some nights anyway. Seed 1 is
# deliberately NOT shopped around for a kinder number: a seed chosen to make the suite look good
# is a measurement tuned to flatter itself. A sim that loses on seed 1 is fragile, full stop, and
# the fix is to make the check roll-independent the way gwdskirmish's startX check already was.
#
# To re-measure one entry: SIM_SEED=random for the old free-running behaviour, SIM_SEED=<n> for a
# different dice. Several seeds failing means the sim is broken; one seed failing means the check
# depends on the roll. Both belong here; they are different debts.
